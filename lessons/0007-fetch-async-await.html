fetch, async & await: the value that isn’t here yet

One idea: some values take time to arrive, so JavaScript hands you a Promise — a receipt for a value that isn’t ready — and await is you waiting at the counter until it is. Today you write the actual JavaScript that sends the request you mapped in Lesson 6 and hands you the response. Happy path only: what to do when it goes wrong is Lesson 8. About 25 minutes.

I’m your teacher for this. This is the lesson where async JavaScript finally arrives — and it arrives with a real reason, not as an abstract exercise. A network round trip takes time, so the code that starts it can’t just hand you the answer on the next line; it has to hand you something that stands in for the answer until it’s ready. That stand-in is the whole concept. If any output on your screen doesn’t match what I describe — especially when you deliberately break it — stop and tell me. Reading what actually came back is the skill.

Why this one now

Last lesson you learned what an API call is — a request you send and a response you read. You even fired one by hand with curl. This lesson is the JavaScript that does that for you: fetch. And it’s the exact shape of your JSM task — send a request to a third party, wait for the answer, read it — so the concept you learn on safe Open-Meteo ground is the same one you’ll point at Atlassian later.

There’s a catch that forces a new idea. A round trip takes time — tens or hundreds of milliseconds. JavaScript runs one thing at a time (it is “single-threaded” — one worker, one task at a time). If that one worker simply stopped and waited for the network, your entire page would freeze — no scrolling, no clicks — until the reply came back. So JavaScript refuses to block. Instead it needs a way to say “start this now, let me carry on, and I’ll deal with the result when it shows up.” That way is the Promise.

The one new idea: a Promise is a receipt

When you start something that takes time, JavaScript can’t give you the result — it isn’t ready. So it gives you a Promise instead: an object that stands in for a value that will arrive later.

The picture to hold

Think of a coat check. You hand over your coat and immediately get a numbered ticket. The ticket isn’t your coat — it’s a claim on a coat that will be handed back later. A Promise is that ticket. And await is you standing at the counter with the ticket until they bring the coat, so that you walk away holding the coat itself, not the ticket.

Here is the whole pattern — the JavaScript version of the curl you ran last lesson. Read it slowly; every line earns its place, and I annotate each below.

getWeather.js — a plain file you run with node getWeather.js

async function findPlace(name) {
  const url = `https://geocoding-api.open-meteo.com/v1/search?name=${name}&count=5`;

  const response = await fetch(url);      // wait #1 — the round trip
  const data = await response.json();     // wait #2 — reading the body

  console.log(data.results);
}

findPlace("Boulder");

Four things are new here. Take them in order:

fetch(url) — the thing that takes time

fetch is the built-in function that sends the request. Because a request takes time, it does not return the response — it returns a Promise (the coat ticket) the instant you call it. Note the backtick string building the URL is your Lesson 1 template literal, and const is habit by now — nothing new there. What’s new is only what fetch hands back.

await — wait for the value, then unwrap it

await sits in front of a Promise and says: pause this function here until the value is ready, then give me the value itself, not the ticket. So await fetch(url) evaluates to the actual Response object — the thing carrying the status code and headers from Lesson 6.

The second await — why there are two

This surprises everyone, and it’s the same idea a second time. fetch’s Promise resolves as soon as the response headers arrive — the status code, the content type — but the body (the JSON you actually want) may still be streaming in over the wire. So reading the body is also a thing that takes time. response.json() returns another Promise, and you await it too. Two things take time → two awaits. Once it resolves, data is the parsed object — the same JSON you saw in curl, now a real JavaScript value you can reach into (data.results).

async — the keyword that licenses await

You can only use await inside a function marked async. That word is the permission slip: it tells JavaScript “this function may pause partway through and resume later, so don’t expect it to finish in one go.” A side effect worth knowing now (it matters in Lesson 8): an async function always hands back a Promise itself — calling findPlace("Boulder") starts the work and returns a ticket of its own.

/jargon — Promise, async, await

Promise: an object that stands in for a value that isn’t ready yet. It will later resolve (the value arrived) or reject (it went wrong — Lesson 8). A function that starts slow work returns one immediately so your program isn’t stuck waiting.

await: put it before a Promise to pause the current function until that Promise resolves, then evaluate to the resolved value (not the Promise). async: the keyword on the function that permits await inside it.

Handle: the Promise is a coat-check ticket — a claim on something not ready yet. await is waiting at the counter until they swap your ticket for the coat. async is the sign on the door saying “people in here are allowed to wait at counters.”

Where the analogy breaks: at a real coat check you stand there idle. The point of a Promise is the opposite — while your function is paused at an await, the single JavaScript worker is free to run other code (handle a click, another request). Your function is parked; the program is not frozen.

In a sentence: “fetch returns a Promise, so I await it to get the Response, then await .json() to get the data.”

Common misuse: forgetting await — then your variable holds the ticket, not the value, and every line after it is working with the wrong thing. That’s the next box, because it’s the bug you’ll meet most.

The bug you’ll see most: the forgotten await

Drop one await and nothing errors — it just goes quietly wrong. Write const response = fetch(url); (no await) and response holds the Promise, not the Response. Ask it for .json() and you get an error like response.json is not a function, because a Promise has no such method — the coat does, the ticket doesn’t. And if you just console.log an un-awaited fetch you’ll see Promise { <pending> } — JavaScript telling you plainly “you’re holding a ticket.”

This is a top reason to read AI-written async code carefully: a missing await looks almost right and runs without crashing at the call site. When you review a fetch, checking that every Promise-returning call is awaited is a concrete, repeatable move — exactly the “say why it’s right or wrong” skill from your mission.

Lesson 8 is the half I held back: error handling. Right now your code assumes the sun always shines. But remember the zzzzz search you ran — 200 OK with no results key at all? And the 404 that Lesson 6 called “a successful round trip”? Here’s the hinge that ties them together: fetch’s Promise only rejects when there was no response at all (network down, bad host). A 404, to fetch, is a Promise that resolved just fine — job done. So “did it work?” becomes a deliberate three-part check: try/catch for “did I get a response?”, then response.ok for the status code, then “is the data actually in the body?” for your empty-200.
