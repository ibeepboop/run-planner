Remotes and Push: getting your code onto GitHub

One idea: a remote is a second, complete copy of your repository on another machine. Git never syncs to it on its own — you push and pull deliberately, exactly like a commit is deliberate. About 20 minutes.

I'm your teacher for this. Nearly everyone's first git push fails once — on authentication, or a "rejected" error — and it feels like you broke something. You didn't; both are normal and both have a clean cause. When you hit one, stop and paste me the exact message. Reading push errors is a skill, and this is where you start it.

Why this one now

Everything you did in Lesson 3 lives in exactly one place: your laptop. Your team's whole workflow — pull requests, review, CI running tests — happens on a shared copy on GitHub. You cannot open a pull request against a copy that doesn't exist yet. This lesson creates that copy and gets your history onto it. It's the floor under the JSM work.

The one new idea

So far "your repo" meant one thing. Now there are two copies of it: the one on your machine, and one on GitHub. They are independent. A commit you make locally is invisible to GitHub until you push it; a change made on GitHub is invisible to you until you pull it. Nothing crosses the gap automatically.

This is the same deliberateness as Lesson 3's commit. Dropbox syncs the instant you save; Git does nothing until you say so. A commit says "remember this locally"; a push says "send these committed snapshots to the other copy." Two separate deliberate acts.

/jargon — remote

Remote: a full copy of your repository hosted on another machine (here, GitHub), that your local repo knows how to talk to. A repo can have several; the first and conventional one is named origin.

Handle: a shared drive the team pushes finished work to and pulls the latest from — except it holds the entire history, not just the current files.

Where the analogy breaks: a shared drive updates live as you edit. A remote updates only when someone pushes to it or pulls from it. And origin is just a nickname for a URL — nothing magic about the word.

In a sentence: "I added the GitHub URL as origin so I could push to it."

Common misuse: thinking the remote is "the real repo" and yours is a copy. All copies are equal in Git — yours is as complete as GitHub's. GitHub is just the copy the team agrees to treat as the shared one.

/jargon — push

Push: sending commits that exist in your local repo but not yet on the remote, so the remote's history catches up to yours.

Handle: uploading — but uploading committed snapshots, not the files currently open in your editor.

Where the analogy breaks: uploading a file replaces whatever was there. Push appends your new commits onto the remote's existing history, and it refuses if doing so would overwrite commits you don't have yet (that's the "rejected" error, and it's protecting you).

In a sentence: "I committed the fix, then pushed so the team could see it."

Common misuse: "push saves my current work." It doesn't touch uncommitted or unstaged edits at all — push only moves things you already committed. Nothing staged-but-not- committed goes anywhere.

The picture

  your laptop                         GitHub
  ┌─────────────┐    git push  ─►    ┌─────────────┐
  │ local repo  │                    │   origin    │
  │ (main)      │   ◄─ git pull      │  (main)     │
  └─────────────┘                    └─────────────┘
  every commit lives here            the shared copy the team uses

push moves commits right; pull moves them left. That's the entire relationship. Pull requests, review and CI are all rituals built on top of this one gap — you'll meet them next lesson.

The authentication reality — read before you push

The moment you first push, GitHub needs to know it's really you. You cannot use your GitHub password — GitHub turned that off for Git in 2021. This trips up literally everyone once, so here's the map.

On Windows, the easy path usually just happens

Git for Windows ships with Git Credential Manager. On your first push it pops open a browser window asking you to sign in to GitHub; you click approve, and it stores a token in Windows for next time. If that window appears — great, follow it, you're done. The options below are for when you want to choose deliberately, or the popup doesn't appear.

MethodHowWhen it suits you
Credential Manager Browser sign-in on first push; nothing to set up. Default on Windows. Start here.
Personal Access Token Create a token in GitHub settings; paste it as the "password" when prompted. The popup didn't appear, or you're on a plain terminal. Treat the token like a password.
SSH key Generate a keypair, add the public half to GitHub, use the git@… URL. You push many times a day and want zero prompts ever. More setup up front.
gh CLI gh auth login once; it configures Git for you. You'll use GitHub's command line anyway. One command, done.

Any of them work; the token or key is just proof it's you. Full, current instructions: GitHub — Authentication. Don't over-study this — try the push, and let the prompt tell you what it wants.

The commands

Two things have to happen: create the empty copy on GitHub, then tell your local repo about it and push.

# 1. On github.com: New repository → name it "run-planner"
#    → do NOT tick "Add a README", ".gitignore", or a licence → Create.
#    (Why empty matters is the gotcha below.)

# 2. Back in your local repo:
git remote add origin https://github.com/<you>/run-planner.git   # name the URL "origin"
git remote -v                                                    # check it stuck
git push -u origin main                                          # send main, and remember the link

That -u (short for --set-upstream) is worth understanding, not just copying. It records that your local main tracks origin/main — so from then on a bare git push or git pull knows where to go, no arguments needed. You set it once per branch.

Why the GitHub repo must be empty

If you let GitHub add a README (or a licence, or a .gitignore), the remote starts with a commit your laptop has never seen. Your push then gets rejected — "updates were rejected because the remote contains work that you do not have locally" — because Git won't silently fuse two unrelated histories. Create it empty and the push is clean. (If you already made it non-empty, don't panic — tell me and we'll reconcile it; it's a two-command fix, not a redo.)

Public or private?

Your call, and both are defensible. Private is the safe default for anything work-adjacent — no one sees it but you. Public makes it a portfolio piece a future employer can read. Run Planner has no secrets (you checked .gitignore last lesson), so either is fine here; if in doubt, private — you can flip it public later in one click.

Your turn — put Run Planner on GitHub

You do every step. I'm here the second anything looks off — especially the first push.

  1. On github.com, create an empty repository named run-planner — no README, no .gitignore, no licence. Choose private or public deliberately.
  2. In your local repo, git remote add origin <the URL GitHub shows you>, then git remote -v to confirm it's registered.
  3. git push -u origin main. If a browser sign-in appears, follow it. If a push error appears instead, read it, then paste it to me — don't guess.
  4. Refresh the repo page on GitHub. Your files and main's history should be there. Find the commit list: you should see three commits — exactly what's on main. The two extra commits on practice-branch are not here, because you pushed main, not that branch. That absence is the lesson working, not a bug.
  5. Stop there. Do not push practice-branch yet — that branch is the star of Lesson 5, where you'll push it and open a real pull request.

The win: your history now exists in two places, and you chose when it crossed the gap.
