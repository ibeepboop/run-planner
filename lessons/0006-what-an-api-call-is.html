What an API call actually is: two messages with a fixed shape

One idea: an API call is a request message you send and a response message you get back — and both have the same predictable anatomy. Once you can name the parts, every API call you read (yours, a teammate's, or one the AI wrote) becomes something you can inspect instead of trust. No code today — just the vocabulary that everything else stands on. About 20 minutes.

I'm your teacher for this. This is the first lesson of the JSM integration proper, and I'm deliberately teaching the concept before any fetch. Your real task — "customer fills our form → we call JSM → a ticket appears" — is one API call. If you can name its parts, you can reason about it; if you can't, you're copying patterns and hoping. We'll use a real, safe call you can run yourself to see every part with your own eyes. If anything you see on screen doesn't match what I describe, stop and tell me — reading a real response is the whole skill.

Why this one now

Your JSM feature comes down to a single sentence: send a request to Atlassian asking it to create a ticket, and read the response to know whether it worked. That's an API call. Before we touch the JavaScript that makes one (fetch, next lesson), you need the map of what an API call is — otherwise the JavaScript is just spells. The API security reference you already have tells you why the JSM token must live on a server; this lesson shows you what that token actually rides inside, and where.

The one new idea

An API call is a conversation of exactly two messages:

  • You send a request — "here is what I want."
  • The server sends back a response — "here is what happened."

The trick that makes this learnable: both messages have the same three-part shape. Learn the shape once and you can read either side. Here is that shape, filled in with your real JSM task on the way out and its answer on the way back.

THE REQUEST  (what your server sends to JSM)
┌───────────────────────────────────────────────────────────────┐
│ POST /rest/servicedeskapi/request        ← METHOD + ENDPOINT   │  the "start line": verb + address
│ Host: your-domain.atlassian.net                                │
│ Authorization: Basic a1b2c3…            ← a HEADER (the token) │  headers: labels about the message
│ Content-Type: application/json          ← a HEADER            │
│                                                                │  ← blank line separates head from body
│ { "serviceDeskId": "10",                 ← the BODY            │  body: the actual payload
│   "summary": "Printer on floor 3 is down" }                    │
└───────────────────────────────────────────────────────────────┘
                          │
                          ▼
THE RESPONSE  (what JSM sends back)
┌───────────────────────────────────────────────────────────────┐
│ 201 Created                              ← STATUS CODE         │  the "start line": did it work?
│ Content-Type: application/json          ← a HEADER            │  headers: labels about the answer
│                                                                │
│ { "issueKey": "SD-42",                   ← the BODY            │  body: the data you asked for
│   "issueId": "10001" }                                         │
└───────────────────────────────────────────────────────────────┘

Same skeleton both ways: a start line, some headers, a blank line, then a body. The only difference is what the start line carries — the request opens with a verb and an address, the response opens with a status code.

/jargon — API call (an HTTP request & its response)

API call: one round trip over HTTP — a request message sent to a specific address, and the response message that comes back. "HTTP" is just the agreed format both messages are written in (the same one your browser uses to load a web page).

Handle: a letter and its reply. You post a letter with an address on the envelope, labels on the outside, and a note inside; you get back a letter with a result stamp, its own labels, and its own note inside.

Where the analogy breaks: a letter is one-way and slow; an API call is a single synchronous round trip — you hold the line and the reply comes back on the same connection, usually in milliseconds. There's no "reply address" because the reply comes straight back down the wire you opened.

In a sentence: "The JSM integration is one API call — we POST the ticket details and read the 201 to confirm it was created."

Common misuse: treating "the API returned something" as "it worked." The response always comes back with a status code — including when it's telling you you got it wrong. Getting a response and getting success are two different things (that's the next section).

The anatomy, term by term

These are the words you'll see in every API doc, every teammate's code, and every fetch the AI writes for you. You only have to play one back to me (the box above); the rest are here as a labelled map to point at, not a memory drill. They'll stick through use.

PartWhat it isEveryday handle
Method
(verb)		 What you're asking the server to do: GET (read), POST (create), PUT/PATCH (update), DELETE (remove). The verb of the sentence. Creating a JSM ticket is a POST; reading a weather forecast is a GET.
Endpoint
(URL)		 The specific address the request is sent to — one URL per operation the API offers. The exact door you knock on. /v1/search is Open-Meteo's "find a place" door; /rest/servicedeskapi/request is JSM's "raise a ticket" door.
Headers Labels about the message — who you are (Authorization), what format the body is in (Content-Type), what you'll accept back (Accept). Writing on the envelope, not the letter inside. The token is a header — which is exactly why the browser can read it, and why it can't live there.
Body The actual payload. On a POST, the data you're sending up (the ticket fields). On a response, the data you asked for (usually JSON). The letter inside the envelope. GET requests usually have no body — you're only asking, not sending.
Status code A three-digit number opening the response that says how it went. This is the first thing you read on the way back. A result stamp. 201 = "made it," 404 = "no such thing," 401 = "who are you?"

Status codes: the number you check first

The status code is grouped into families by its first digit. You don't memorise the list — you memorise the five doorways, then recognise the handful you actually meet.

FamilyMeaningOnes you'll actually see
2xxSuccess. It worked. 200 OK (here's the data), 201 Created (I made the thing).
3xxRedirect — go look somewhere else. Rare in API work; your tools follow these for you.
4xxYou got it wrong. The request was bad. 400 (malformed), 401 (not authenticated), 403 (not allowed), 404 (no such endpoint/record), 429 (too many requests).
5xxThe server got it wrong. Not your fault. 500 (it broke), 503 (it's down/overloaded).

The dividing line worth burning in: 4xx is your bug, 5xx is theirs. When the AI writes JSM code and something fails, that first digit tells you which side to look at — a 401 means fix your token; a 500 means retry or call Atlassian, not rewrite your request.

A 404 is a successful round trip

This is the one that trips everyone, and it sets up next lesson. If you ask for a URL that doesn't exist and get 404 Not Found, the HTTP request itself succeeded — you reached the server, it understood you, and it answered. "Not found" is the answer.

Contrast that with the request never arriving at all (server down, no internet, wrong host) — that's a failure, because there's no response at all. So there are two different questions, and you must ask them in order: (1) did I get a response? then (2) what status code was it? Next lesson you'll see fetch treat a 404 as a perfectly successful call for exactly this reason — and it surprises almost everyone until they've seen this box.

A 200 can still be "empty" — check the body too

Status is necessary but not sufficient. Open-Meteo's geocoding endpoint answers a no-match search — say name=zzzzz — with a cheerful 200 OK whose body is just {"generationtime_ms":0.69}: the results key is absent entirely. The call succeeded; there's simply nothing in it. So "did it work?" is really two checks — a good status code and a body that actually contains what you need. You'll meet this exact response again when we type it.

Where the auth token rides — and why that's the whole security story

Look back at the request diagram: the token is a header (Authorization). That single fact is the root of your entire API security reference. If your Vue app in the browser made the JSM call directly, the browser would have to write that header itself — which means the token would have to be in code the browser downloaded, where any user can open devtools and read it. The token isn't leaked by carelessness; it's leaked by architecture, the moment the request originates in the browser. That's why the request has to be built on your server, where the header is attached out of the user's sight. You'll build that server later (Lessons 13–14); for now, just hold the link: token = a request header = a thing the browser can read = a thing the server must add instead.

Two real calls, side by side

Your practice ground is deliberately the safe one. Open-Meteo needs no token, so you can fire real requests at it all day and see every part of this lesson live — while it's the exact same shape as the JSM call you can't experiment on freely.

PRACTICE (safe — no token, you can run this yourself)
  GET /v1/search?name=Boulder&count=5      ← method GET, endpoint + query
  Host: geocoding-api.open-meteo.com
  (no Authorization header — public data)
  (no body — a GET only asks)
        ▼
  200 OK
  { "results": [ { "name": "Boulder", "admin1": "Colorado", … },
                 { "name": "Boulder", "admin1": "Montana",  … } ] }

WORK (the same shape, plus a token and a body)
  POST /rest/servicedeskapi/request           ← method POST, endpoint
  Host: your-domain.atlassian.net
  Authorization: Basic …                       ← the header that must be added server-side
  Content-Type: application/json
  { "summary": "Printer down", … }             ← the body: what to create
        ▼
  201 Created
  { "issueKey": "SD-42", … }

Read across: GET vs POST, no-token vs token-in-a-header, no-body vs body, 200 vs 201. Different values, identical anatomy. When you can look at either and point to each part by name, you can read any API call in your codebase.

Your turn — make a real request and read every part of the response

No app, no code file — you're going to fire a genuine API call and see this lesson's anatomy in the wild. Two ways; do the terminal one, and the browser one if you want to see the request side too.

  1. Terminal (PowerShell). Run:
    curl.exe -i "https://geocoding-api.open-meteo.com/v1/search?name=Boulder&count=5"
    The -i flag says "include the response headers." Read the very first line — that's your status code (expect 200). Below it, the headers (find Content-Type: application/json). Then a blank line, then the body — the JSON. (Use curl.exe, not curl — in PowerShell bare curl is an alias for a different command.)
  2. Now break it on purpose. Run the same command with name=zzzzz. What status code comes back — and is the results key in the body? Tell me what you see; this is the "200 but empty" gotcha, live.
  3. Browser (optional, to see the request side). Open the Boulder URL in a browser tab. Then open devtools (F12) → Network tab → reload. Click the search request. You'll see the request method (GET), the request headers your browser added, the response status, and the response body — the whole two-message exchange, itemised by the browser, using this lesson's exact words as its section labels.

The win: you sent two real API calls, read a success and a "successful failure," and located every part — method, endpoint, header, body, status code — in an actual response. That's the reading skill the whole JSM task rests on.

Then play one thing back to me in your own words: what is an API call? Describe the two messages and, in each, where the important parts live — especially which part you read first to know if it worked, and which part carries the token. When that's solid it goes in your glossary, and we move to fetch — the JavaScript that actually sends one.
