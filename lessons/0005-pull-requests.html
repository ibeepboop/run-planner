Pull Requests: proposing a merge, GitHub's way

One idea: a pull request is a proposal to merge one branch into another — and unlike the merge you know, it happens on GitHub, after review, not on your laptop. That single relocation is why you push before you merge, and it puts your "push it up" instinct exactly where it belongs. About 25 minutes.

I'm your teacher for this. This is the exact workflow your team runs on, and the last pure-Git thing standing between you and the JSM integration. It has more moving parts than a commit, so we go one observation at a time — you'll watch the merge move from your laptop to GitHub and back. If any screen doesn't look like what I describe, stop and tell me before you click. Reading a PR screen is a skill too.

Why this one now

In Lesson 3 you merged branches yourself, locally, with git merge — and last lesson you declined to fake a merge so we could do the real thing here. This is the real thing. No one on a team merges their own branch straight into main on their laptop. They propose the merge, someone reviews it, and GitHub performs it. That proposal is a pull request. Every change you ship at work — including the JSM feature — will travel through one.

The one new idea

You already know how to merge: git merge takes one branch's commits and folds them into the branch you're on, on your machine. A pull request keeps the same goal — fold practice-branch into main — but changes where and when it happens:

  • Where: on GitHub's copy, not your laptop. The merge button lives on the website.
  • When: after the change has been looked at — a diff to read, a place to comment, a check that has to pass.

Here's the consequence that resolves the thing that kept tripping you up. Because the merge runs on GitHub, GitHub has to be able to see your branch's commits first. So the order is forced: push the branch up, then merge it up there. Your "push it up" instinct was never wrong — it was just early. Push is how the branch gets to the place where the merge can happen.

/jargon — pull request (PR)

Pull request: a request, opened on GitHub, to merge the commits on one branch (here practice-branch) into another (here main). It bundles the diff, the commits, a discussion thread, and a merge button into one page.

Handle: a merge request with a cover note — "please pull these commits of mine into main" — that a teammate reads and approves before it goes in.

Where the analogy breaks: the name is backwards from what it feels like. You're offering your commits, but it's called a pull request because you're asking the project to pull them in. GitHub named it from the receiver's side, not yours.

In a sentence: "I pushed the branch and opened a PR so Sam could review it before it hit main."

Common misuse: thinking the PR is the merge. It isn't — it's the proposal. The branch isn't merged until someone clicks the button. An open PR can sit, get comments, get more commits pushed to it, or be closed without ever merging.

Read the bottom diagram top to bottom: the branch goes up, the merge happens up there, and the merged main only reaches your laptop when you git pull it back down. Three deliberate moves, and the merge is the middle one — on GitHub.

The commands and clicks

Half of this is terminal, half is the website. I've marked which is which.

# TERMINAL — push the branch up, still unmerged.
git switch practice-branch           # make sure you're on it
git push -u origin practice-branch   # send it; -u links it to origin, same as main last lesson

# WEBSITE — github.com shows a yellow banner: "practice-branch had recent pushes …
#   Compare & pull request".  Click it.
#   base: main   ◄──   compare: practice-branch     (merge INTO main, FROM your branch)
#   Give it a title, then "Create pull request".

# WEBSITE — read your own PR. The "Files changed" tab is the diff; "Commits" shows your two.
#   This is the review view your teammates will use. Read it as if it were someone else's.

# WEBSITE — click "Squash and merge" (see the box below on which button), then "Confirm".
#   Optionally click "Delete branch" — safe, it only deletes the copy on GitHub.

# TERMINAL — bring the merged main back down.
git switch main
git pull                             # main now has the merged change; -u from Lesson 4 means no args
git log --oneline                    # see the new commit that the merge created on main

Notice the -u again: you set it once per branch. You did it for main last lesson; practice-branch is a different branch, so it needs its own. After this, a bare git push from that branch knows where to go.

Which merge button? — GitHub offers three

When you go to merge, GitHub gives you a dropdown. This is a real decision, so here's which suits what, not just a "recommended" sticker:

ButtonWhat it doesWhen it suits you
Squash and merge Collapses all the branch's commits into one new commit on main. The default on most teams. Your two "work in progress" commits become one clean entry in main's history. Use this today.
Merge commit Keeps every branch commit and adds one extra "merge commit" tying them together. When each commit is meaningful on its own and you want the full trail preserved.
Rebase and merge Replays your commits onto main individually, no merge commit. When you want every commit kept but a dead-straight history. The advanced option — leave it for now.

We use squash today because your two practice commits ("update a line", "add prediction") aren't history anyone needs — one tidy commit on main is the honest record. Your team likely has a house rule; ask which they use, and match it.

Squash makes a brand-new commit — but your pushed branch is still safe to delete

Squash doesn't move your two commits onto main; it writes a new one that contains the same changes but has a different identity. So practice-branch is not merged into main — and you might expect git branch -d practice-branch to refuse.

It won't, and the reason is pure local-vs-remote. -d checks "is this branch fully merged into its upstream?" first, and only falls back to checking main/HEAD if there's no upstream. Because you pushed with -u, the upstream origin/practice-branch holds the same commits — so Git sees them as safe and deletes the branch, printing a warning that it's merged to origin/practice-branch but not to HEAD. Read that warning; it's telling you exactly which copy vouched for the commits.

You'd only need the force flag git branch -D practice-branch if no copy survived — e.g. you deleted the branch on GitHub and ran git fetch --prune, so the remote-tracking ref is gone too. Then -d falls back to main, can't find the squashed commits under their old identity, and refuses. (Either way, confirm the change is on main with git log before deleting anything.)

"base" and "compare" point the way the merge flows

On the PR screen, base is where the commits are going (main) and compare is where they're coming from (practice-branch). Get these backwards and you'll propose merging main into your branch — the opposite of what you want. GitHub usually guesses right, but read it before you click, the same way you read a push error.

Your turn — ship practice-branch through a real PR

You do every step. I'm on standby the instant a screen or a message looks off.

  1. git switch practice-branch, then git push -u origin practice-branch. Confirm it lands: GitHub should now show the branch (it didn't last lesson — that absence was the Lesson 4 proof).
  2. Open the pull request from the banner GitHub shows you. Check base = main, compare = practice-branch. Title it something honest and create it.
  3. Open the Files changed tab and read your own diff. Then Commits — you should see your two commits. Tell me what the diff shows before you merge; reading it is half the point.
  4. Squash and merge → Confirm. Watch the PR flip to a purple "Merged" state.
  5. Back in the terminal: git switch main, then git pull. Run git log --oneline. You should see one new commit on main — the squash — carrying practice-branch's changes. That commit was born on GitHub and just travelled down to you.
  6. Optional tidy-up: run git branch -d practice-branch. It deletes the branch and prints a warning that it was merged to origin/practice-branch but not to HEAD — read that line, it names the copy that made the commits safe (the squash gotcha above). You'd only need the force flag -D if you'd also pruned that remote-tracking copy.

The win: you ran your team's real ship-it loop end to end — pushed a branch, proposed a merge, reviewed it, merged it on GitHub, and pulled the result home — and you chose every moment it moved.

Then play one term back to me in your own words — pull request — and it goes in your glossary. The question I most want you to answer: why does the push have to come before the merge? If that one clicks, the local-vs-remote picture is finally whole.
