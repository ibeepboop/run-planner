Error handling: three ways “wrong” looks

Last lesson you wrote the happy path and it worked first time — that’s the trap. Real code has to ask “did it actually work?” and that question splits into three separate checks, because fetch only tells you about one of them. You’ve already seen two of the three go wrong — today you name them and handle them on purpose. About 25 minutes.

I’m your teacher for this. This lesson has one idea wearing three coats: “did it work?” is not one question, it’s three, and each one needs a different piece of code. If any output on your screen doesn’t match what I describe — especially the two failures you trigger on purpose — stop and tell me exactly what you see. Reading the mismatch is the skill, same as last time.

Why this one now

Your getWeather.js from Lesson 7 assumes the sun always shines: the network is up, the host answers, the status is good, and the body has what you asked for. Every one of those can fail independently, and you’ve already watched two of them happen with your own eyes:

  • You ran curl.exe -i against a made-up place, zzzzz, and got back 200 OK — a good status — with no results key at all.
  • Lesson 6 called a 404 “a successful round trip” — the server answered, it just answered “not found.”

Neither of those is a network failure. fetch did its job in both cases. That’s the hinge for today.

The one idea: “did it work?” is three separate checks

fetch’s Promise only rejects — the thing catch catches — when there was no response at all: the network is down, the host doesn’t exist, the request never completed. That’s a narrower event than “something went wrong” — a 404 or a 500 is still a response, so as far as the Promise is concerned, it resolved fine. So you need three checks, stacked, each answering a question the one before it can’t:

The picture to hold

Think of mailing a letter. Check 1 is “did the letter even get delivered, or did it bounce back to me undeliverable?” (no address exists — you never hear from the recipient at all). Check 2 is “the letter arrived — what does the reply say?” It might say “yes,” or it might say “no such person here” — either way, you got a reply, so check 1 already passed. Check 3 is “the reply says ‘yes’ — but did they actually enclose the document I asked for, or is the envelope empty?”

getWeather.js — Lesson 7’s happy path, about to grow three checks

async function findPlace(name) {
  const url = `https://geocoding-api.open-meteo.com/v1/search?name=${name}&count=5`;

  const response = await fetch(url);
  const data = await response.json();

  console.log(data.results);
}

Check 1 — try/catch: did a response come back at all?

This is the only one of the three that fetch’s Promise itself signals, by rejecting. An await on a rejected Promise throws — and try/catch is how JavaScript lets you catch a throw without crashing the whole program.

try {
  const response = await fetch(url);
  // ...
} catch (err) {
  console.log("No response at all:", err.message);
}

Everything that can throw — both awaits — needs to sit inside the try block, because either one could be the line that fails.

Check 2 — response.ok: was it a good status?

Once you’re past catch, you have a real Response object — fetch did its job. But “did its job” and “good news” are different things. response.ok is a boolean shortcut: true for status codes 200–299, false for everything else, including your 404. You check it before you trust the body:

if (!response.ok) {
  console.log("Bad status:", response.status);
  return;
}

Check 3 — is the thing you asked for actually in the body?

This is your zzzzz case, and it’s the one no built-in shortcut checks for you — it’s specific to this API’s contract, not HTTP in general. A 200 with an absent results key passes both checks above and still isn’t what you wanted:

if (!data.results) {
  console.log("No matches for that name.");
  return;
}

Put together, all three checks in one function:

async function findPlace(name) {
  const url = `https://geocoding-api.open-meteo.com/v1/search?name=${name}&count=5`;

  try {
    const response = await fetch(url);           // check 1 lives around this

    if (!response.ok) {                           // check 2
      console.log("Bad status:", response.status);
      return;
    }

    const data = await response.json();

    if (!data.results) {                          // check 3
      console.log("No matches for that name.");
      return;
    }

    console.log(data.results);
  } catch (err) {                                 // check 1's other half
    console.log("No response at all:", err.message);
  }
}
/jargon — try/catch, response.ok

try/catch: a block that runs code which might throw, and a second block that runs only if it did, instead of crashing the program. An await on a rejected Promise is one way to throw.

response.ok: a boolean on the Response object — true for HTTP status 200–299, false otherwise. It does not look at the body at all, only the status line.

Handle: try/catch is “did the letter bounce back undeliverable?” response.ok is “the reply arrived — does it say yes?”

Where the analogy breaks: a real bounced letter and a real “no” reply look different in your mailbox. In code, both a network failure and ignoring response.ok can look deceptively similar if you don’t check — your code just carries on to .json() either way unless you stop it.

In a sentence: “I wrap the fetch in try/catch for network failure, then check response.ok before I trust the body.”

Common misuse: assuming catch alone is “error handling done.” A 404 never throws — it sails straight past catch and into your .json() call looking like success, unless response.ok stops it first.

The bug you’ll see most: trusting catch to mean “handled”

AI-generated fetch code very often has a try/catch and stops there — it looks defensive. But a 404 or 500 resolves the Promise just fine, so it never enters catch at all. Code that only wraps fetch in try/catch will happily try to read the body of an error page as if it were your data. When you review someone’s fetch call, ask specifically: where’s the response.ok check? If it’s missing, that’s a real gap, not a style nitpick — exactly the “say why it’s right or wrong” skill from your mission.

Your turn — add all three checks, then break each one on purpose

Start from your working getWeather.js and grow it. Write the checks yourself from the pattern above — don’t paste mine verbatim.

  1. Add all three checks to findPlace: try/catch around both awaits, a response.ok check with a status log, and a data.results presence check.
  2. Trigger check 1: change the URL’s hostname to something that doesn’t exist — e.g. https://this-host-does-not-exist.invalid/... — and run it. Read what lands in err.message. Confirm your catch block, and only that block, ran.
  3. Trigger check 2: find or construct a URL that returns a real 404 against Open-Meteo (a wrong path segment works — e.g. swap /v1/search for /v1/nonsense). Confirm catch did not run and your response.ok branch caught it instead.
  4. Trigger check 3: search for "zzzzz" again, now through your updated function. Confirm it prints your “no matches” message instead of crashing on undefined.

The win: three real, distinct failures, each caught by the specific check built for it — not one catch-all that quietly misses two of the three.

Then play it back to me in your own words: what does try/catch actually catch, what does response.ok catch that it doesn’t, and what does check 3 catch that neither of the others can see? When that’s solid, try/catch and response.ok go in your glossary.
