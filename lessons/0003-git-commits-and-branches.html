Git: Commits and Branches

One idea: Git stores snapshots you chose to take. Branches, pull requests and everything else follow from that. Practised on Run Planner, which has zero commits and no remote — nothing here can break anything. About 25 minutes.

I'm your teacher for this. Git is the topic where people nod along and stay quietly lost for years, because the vocabulary is genuinely bad. If a word doesn't land, stop and ask. That's not falling behind — that's the lesson working.

Why this one first

You have work on your laptop that isn't committed, in a repo whose conventions you don't know yet, with ten days on the clock. Until you can commit and branch confidently, every hour of work you do is stored in exactly one place and mixed in with every other change you've made. This lesson is the floor you need before the JSM integration, not a detour around it.

The one new idea

Git is not a backup system, and it is not a sync system. It is a sequence of snapshots that you deliberately took, each with a note saying why.

That word deliberately is the whole thing. Dropbox saves your file when you save your file. Git saves nothing until you say "this, now, is a state worth remembering." The cost is one extra step; the payoff is a history of meaningful moments rather than a pile of autosaves.

/jargon — commit

Commit: a permanent, named snapshot of the whole project at one moment, plus a message explaining the change and a link to the snapshot before it.

Handle: a save point in a game. You choose when to drop one, you can return to it later, and the ones you didn't take don't exist.

Where the analogy breaks: returning to a game save wipes what came after. Git keeps everything — going back to an old commit doesn't destroy the newer ones. And a commit is the entire project, not just the file you were editing.

In a sentence: "I committed the form validation separately so it can be reviewed on its own."

Common misuse: treating a commit as "saving my work at the end of the day." A commit should be one coherent change. Ten unrelated edits in one commit is a commit nobody can review, revert, or understand later.

The three places a file can be

This is the part that confuses everyone, and it's worth five minutes because every Git command you'll ever run moves files between these three:

working directory  →  staging area  →  repository
(your edits)          (chosen for       (committed
                       the next          history)
                       commit)

Perl has no equivalent, so there's nothing to lean on here — it's just new.

/jargon — staging area

Staging area (also called the index): a holding space where you assemble exactly the changes that will go into your next commit.

Handle: the counter at a checkout. Your basket is everything you've picked up; the counter is what you're actually paying for this trip. You can leave things in the basket.

Where the analogy breaks: staging copies a change rather than moving it — the file stays in your working directory too. And you stage a version of a file: edit it again after staging, and the newer edit isn't staged.

In a sentence: "I staged just the CSS changes and left the debug logging out of the commit."

Common misuse: assuming git commit commits everything you've changed. It commits what you staged. This is why people are baffled when a file they edited isn't in the commit.

Why does staging exist at all? Because real work is messy. You set out to fix a bug, and along the way you also renamed a variable and left three console.logs in. Staging lets you commit the fix by itself and deal with the rest separately — so the history says what happened instead of when you stopped for lunch.

The commands

git status                  # what's changed, what's staged — run this constantly
git add <file>              # stage one file
git add .                   # stage everything changed, from here down
git commit -m "message"     # snapshot what's staged
git log --oneline           # the history, one commit per line
Run git status until it's a reflex

It is the only command that answers "where am I and what have I done?" and it is read-only — it can never break anything. Experienced engineers run it dozens of times an hour. If you adopt one habit from this lesson, make it this one.

What a commit message is for

The message is read by a future person deciding whether your commit is the one that broke something. Write for that reader.

git commit -m "stuff"                                  # useless
git commit -m "fix"                                    # useless
git commit -m "Add pace calculation to forecast list"  # useful

The convention is the imperative mood — "Add", "Fix", "Remove", not "Added" or "Adding". The reason is that the message completes the sentence "Applying this commit will…". It'll look odd for a week and then be invisible.

Branches

Everything so far was one line of history. A branch lets you have more than one.

/jargon — branch

Branch: a movable name pointing at one commit, marking one line of development. Committing on a branch moves the name forward.

Handle: a bookmark in a choose-your-own-adventure book. Several bookmarks, one book, each marking where a different storyline got to.

Where the analogy breaks: a bookmark is passive; a branch name follows you automatically as you commit. And branches can be merged back into one storyline, which books can't do.

In a sentence: "I built the ticket form on a branch so main stayed deployable."

Common misuse: thinking a branch is a copy of the folder. It isn't — it's a pointer. That's why branching is instant even on a huge repo.

git branch                        # list branches; * marks where you are
git switch -c feature-ticket-form # create a branch and move onto it
git switch main                   # move back

Why professionals never commit to main directly: main is the version everyone agrees is good — often the version that gets deployed. Work in progress on main means everyone else inherits your half-finished feature. Work on a branch is invisible to everyone until you offer it.

This matters for you specifically: check what branch you're on before you touch your work repo again. If you've been building the front end directly on main, that's worth fixing now, while it's small. Ask me and I'll walk you through moving it.

Your turn — Run Planner has zero commits. Fix that.

Everything below is on your repo with no remote. Nothing can reach anyone else.

  1. Run git status and read it properly. Every file is "untracked" — Git has never been told to care about them.
  2. Open .gitignore and confirm node_modules is listed. Then explain to me why that folder must never be committed. (This one bites people in real repos.)
  3. Stage and commit the project scaffolding on its own — package.json, vite.config.ts, the tsconfig files, .gitignore, index.html, src/, public/. One commit, imperative message.
  4. Now a second, separate commit for the course material — MISSION.md, NOTES.md, lessons/, assets/, reference/, learning-records/, RESOURCES.md, scratch/. Two commits, because these are two unrelated things.
  5. git log --oneline. Two lines. That's your history.
  6. Make a branch: git switch -c practice-branch. Add a line to scratch/02-lists.js, commit it, then git switch main and look at the file. Predict what you'll see before you look.
  7. git log --oneline on main. Is your third commit there? Why not?

Step 6 is the one that makes branches click. Write your prediction down first.
