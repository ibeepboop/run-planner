Callbacks, .map() and .filter()

One idea: a function can be an argument. Everything else in this lesson follows from it. Still plain Node, no Vue, no build step. About 20 minutes.

I'm your teacher for this. If a bit doesn't land, say so — including "this is still pitched too high". That feedback is more useful to me than you struggling through. Ask anything.

The win

By the end you'll be able to read a line like days.filter(d => d.rain < 20).map(d => d.date) and say out loud what comes out of it, and how many items it has. That line shape is most of what a Run Planner does to a forecast.

Part 1: the one new idea

Last lesson you proved this yourself, and it's the whole foundation:

const double = n => n * 2

console.log(double)      // [Function: double]  ← the function itself
console.log(double(5))   // 10                  ← the result of calling it

The name double holds the function. The parentheses are what calls it. Those are two separate things, and once they're separate, a new move becomes possible: you can hand the uncalled function to something else and let it do the calling.

/jargon — callback

Callback: a function passed as an argument to another function, which that other function calls at a time of its choosing.

Handle: leaving a phone number. You don't decide when the call happens — you hand over the means to make it, and the other party calls when they're ready.

Where the analogy breaks: a phone number is a way to reach you; a callback is the code itself. And .map() calls it immediately and repeatedly — once per item — not later and once.

In a sentence: ".map() takes a callback and runs it against every element of the array."

Common misuse: writing days.map(double(n)) — that calls double yourself and passes the result. You want days.map(double), where double has no parentheses of its own.

Whose parentheses are these?

There are two separate pairs in play, and only one of them is on screen:

days.map(double)
        ↑      ↑
        these belong to map — they hold its argument list

.map is being called; its argument is double. The pair that would call double is a different pair, and it's absent on purpose:

days.map(double)      // argument is the function itself → map calls it, once per day
days.map(double(n))   // argument is double's return value → map gets a number, and fails

In the second line JavaScript evaluates double(n) before .map ever starts. To tell whose parentheses you're looking at, read the name immediately to the left of the (.

You have done this in Perl, though Perl hides the seam. In map { $_ * 2 } @nums the block is the callback — Perl just gives it special syntax instead of making it a value you could name.

Part 2: .map() — same length, different contents

Perl

my @nums    = (1, 2, 3);
my @doubled = map { $_ * 2 } @nums;   # (2, 4, 6)

JavaScript

const nums    = [1, 2, 3]
const doubled = nums.map(n => n * 2)   // [2, 4, 6]

Three differences worth naming, because they're the ones that trip people up:

  • .map() is a method on the array — it hangs off the array with a dot, rather than taking the list as an argument.
  • The callback has a real parameter name (n) instead of Perl's implicit $_. You choose the name, and a good one is worth a comment.
  • It returns a new array. nums is untouched — exactly as you described it back to me last session.

The defining property: the output array always has the same length as the input. One in, one out, every time. If you find yourself wanting to skip some, you don't want .map().

Part 3: .filter() — same contents, fewer of them

Perl's grep, respelled:

Perl

my @warm = grep { $_ > 15 } @temps;

JavaScript

const temps = [9, 18, 22, 12]
const warm  = temps.filter(t => t > 15)   // [18, 22]

Same callback idea, different contract. .filter()'s callback is asked a yes/no question about each element: return something truthy to keep it, falsy to drop it. The elements that survive come through unchanged.

The distinction to hold on to

.map() — same length, new values. The callback returns a replacement.

.filter() — same values, new length. The callback returns a verdict.

Mixing them up is the single most common mistake with these two. If your callback returns true/false to .map(), you get an array of booleans and no error message.

MDN — Array.prototype.filter()

Part 4: chaining

Because both return an array, you can hang the next call straight off the result:

const temps = [9, 18, 22, 12]

temps.filter(t => t > 15).map(t => `${t}°C — go`)   // ['18°C — go', '22°C — go']

Read it strictly left to right: start with four numbers, keep two, turn those two into two strings. Order matters — filtering first means .map() does less work and, more importantly, never sees the values you rejected.

Now read some code and judge it

This is the skill that pays off at work, so it gets its own question. Someone hands you this, claiming it "gives the dates of the good running days":

const goodDays = days.map(d => d.rain < 20)

What is actually in goodDays?

Your turn — 15 minutes, in a scratch file

Create scratch/02-lists.js and run it with node scratch/02-lists.js. Start by pasting this sample forecast — it's shaped like what Open-Meteo will eventually give us, once we've reshaped it:

const days = [
  { date: '2026-07-25', tempMax: 31, rain: 5 },
  { date: '2026-07-26', tempMax: 19, rain: 60 },
  { date: '2026-07-27', tempMax: 22, rain: 10 },
  { date: '2026-07-28', tempMax: 17, rain: 0 },
  { date: '2026-07-29', tempMax: 28, rain: 45 }
]

Reach for d.rain and d.tempMax to get at the fields — dot notation, like Perl's $d->{rain}.

  1. Use .map() to log an array of just the dates. Check the length is five.
  2. Use .filter() to keep the days with rain under 20. Log it and confirm you got whole day objects back, not just dates.
  3. Chain them: good days → an array of sentences like "2026-07-27: 22°C, 10% rain", built with a template literal.
  4. Log days.length at the very end to prove nothing was mutated.
  5. Break it on purpose: swap the two — .map() the condition and .filter() the sentence — and look at what you get. Predict the output before you run it, then check whether you were right.

Declare all of these with const. Nothing here is ever reassigned, and let tells a future reader — including you — that it might be.
