TypeScript from the ground up

Everything in getWeather.js still works — and everything in it is untyped. Nothing stops you writing data.resutls instead of data.results and finding out at runtime, if you find out at all. Today: the two pieces of syntax that fix that, and an honest look at what they actually check and when. About 25 minutes.

I’m your teacher for this. TypeScript has a lot of surface area — today is deliberately narrow: annotations and interface, nothing else. If a term shows up that I haven’t defined, stop and ask rather than guessing past it.

Why this one now

Lesson 8 gave getWeather.js three checks for “did it work?” — but every value in that function is still whatever JavaScript decides it is at the moment. data could be anything. data.results and data.resutls look identical to your editor: both are just a property read that might be undefined. Nothing before runtime tells you which one you actually typed.

TypeScript’s whole pitch is: you write down the shape you expect, and something checks reality against it before the code runs — not after, the way your check-3 if (!data.results) does. Worth being precise about what that buys you, though — it doesn’t make check 3 disappear. You’ll see why by the end of this lesson.

The one idea: a written-down shape, checked before you run

Plain JavaScript has types — every value is a number, a string, an object, whatever — but nothing makes you declare them, and nothing stops you passing the wrong one. TypeScript adds a layer on top: you annotate what a value should be, and a checker compares your code against those annotations. Get it wrong, and you find out while you’re still typing, in your editor — not three weeks later when a user searches for a place with no results.

Annotating a function

The most common place you’ll write a type is on a function’s parameters and return value:

function double(n: number): number {
  return n * 2;
}

n: number says “this parameter must be a number.” The : number after the closing ) says “this function returns a number.” Call double("5") in an editor that understands TypeScript, and it tells you right there: Argument of type 'string' is not assignable to parameter of type 'number'. You never ran the code. You don’t need to.

Interface: the shape of an object

A function signature covers one value at a time. Most of what you’ll type is an object with several properties — a geocoding result, a forecast day, a user. interface names that shape once, so you can reuse it:

interface Point {
  x: number;
  y: number;
}

function distanceFromOrigin(p: Point): number {
  return Math.sqrt(p.x ** 2 + p.y ** 2);
}

Now write p.z anywhere in that function, and your editor says Property 'z' does not exist on type 'Point'. That’s the data.resutls typo, caught the same way — if data is typed as an interface instead of left as whatever JavaScript infers.

Optional properties: the honest version of a shape

Not every property is always there. You already know one case by heart: the geocoding API’s results key is absent entirely when nothing matches — not [], not null, gone. A ? after the property name tells TypeScript that’s allowed:

interface GeocodingResponse {
  results?: GeocodingResult[];   // absent when nothing matches
}

Here’s the part worth sitting with: once results is marked optional, TypeScript will not let you write data.results.length without checking first — it flags Object is possibly 'undefined'. Your check-3 if (!data.results) from Lesson 8 isn’t made redundant by this — it’s the thing the type system is now forcing everyone who touches this code to keep doing, instead of trusting them to remember.

Types are a claim, not a guarantee

response.json() hands you back a value typed any — TypeScript has no way to know what a server actually sent. Writing interface GeocodingResponse and asserting the JSON into that shape is a promise you’re making, not something verified against the network. If the promise is wrong — you typed a field that isn’t optional but sometimes is — the checker stays quiet and you’re back to a runtime surprise. This is exactly why the shape has to match reality, verified fields and all, not what looks tidy.

The gotcha that catches almost everyone once

Run this yourself before reading on. Save it as a .ts file and run it with plain node, no compiler, nothing installed:

function double(n: number): number {
  return n * 2;
}

console.log(double("5"));

Guess what happens, then run node yourfile.ts. It prints 10. No error, no warning, nothing. "5" got multiplied like a number and JavaScript quietly coerced it.

Node doesn’t check types — it erases them

Modern Node (yours is v24) can run .ts files directly, but all it does is strip the annotations out before running — n: number becomes plain n, as if you’d deleted every colon-type yourself. It never compares your call against the annotation. The checking happens somewhere else entirely: your editor’s TypeScript language service (VS Code ships one built in, no install needed), or the standalone compiler, tsc, run separately. “It ran without error” and “it’s type-correct” are two different claims — today is the first time those have come apart for you.

/jargon — type annotation, interface

Type annotation: the : number / : string / : SomeInterface you write after a variable, parameter, or function signature, declaring what shape that value must have.

Interface: a named, reusable description of an object’s shape — which properties it has, their types, and which are optional.

Handle: an annotation is a label on one box. An interface is the label template you stamp onto every box of that kind, so you only design the label once.

Where the analogy breaks: a real label doesn’t stop you putting the wrong thing in the box — TypeScript’s checker actively refuses to compile code that does, or at minimum lights it up red in your editor. The label enforces itself, at edit time, before anything runs.

In a sentence: “I gave GeocodingResponse an interface with results marked optional, so the compiler makes me handle the no-match case instead of letting me forget it.”

Common misuse: treating a passing tsc run (or a clean-looking editor) as proof the data is correct. It only proves your code is internally consistent with the shape you wrote down — see the callout above. A wrong interface compiles just as cleanly as a right one.

Your turn — write it, break it, watch where each check actually lives

New file: scratch/typescript-fundamentals-practice.ts. Write everything yourself from the patterns above — don’t paste mine verbatim.

  1. Write a typed function with at least one parameter annotation and a return type — doesn’t have to be double, pick anything small.
  2. Write an interface with at least two properties, one of them marked optional with ?. Reuse GeocodingResult’s real shape from the Open-Meteo reference if you want it to pay forward.
  3. Write a function that takes your interface as a parameter, and inside it, deliberately access a property name that doesn’t exist on the interface (a typo, on purpose). Open the file in VS Code and confirm you get a red squiggle without running anything.
  4. Now run the whole file with node scratch/typescript-fundamentals-practice.ts. Does it run despite the squiggle? Read what actually happens and be ready to explain why, in terms of what Node does versus what your editor does.
  5. Trigger the optional-property check: try to read a property off your optional field without checking it first (e.g. .length on the optional array). Confirm your editor objects, then fix it with an if check and confirm the squiggle disappears.

The win: you’ve now watched, with your own eyes, that a type error and a runtime error are not the same event, and that they’re caught by two completely different things.

Then play it back to me: what does an annotation actually check, what does marking a property optional force you to do, and what part of this catches nothing at all if you only ever run your file with plain node? When that’s solid, type annotation and interface go in your glossary.
