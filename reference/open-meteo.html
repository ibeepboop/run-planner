Open-Meteo API

Endpoints, parameters and response shapes. Verified against live responses on 21 July 2026.

Two separate APIs, two different hosts. Neither needs an API key for non-commercial use. Both send permissive CORS headers, so the browser can call them directly.

Geocoding — name to coordinates

https://geocoding-api.open-meteo.com/v1/search
ParamNotes
nameRequired. 2 chars = exact match only; 3+ = fuzzy match.
countDefault 10, max 100.
languageDefault en.
countryCodeISO-3166-1 alpha-2 filter, e.g. US.

GET /v1/search?name=Boulder&count=2

{
  "results": [
    {
      "id": 5574991,
      "name": "Boulder",
      "latitude": 40.01499,
      "longitude": -105.27055,
      "elevation": 1624.0,
      "timezone": "America/Denver",
      "country": "United States",
      "country_code": "US",
      "admin1": "Colorado",      // state / region
      "admin2": "Boulder",       // county
      "population": 106803
    }
    // ... second result: Boulder, Montana
  ],
  "generationtime_ms": 0.45
}
Gotcha

When nothing matches, the response is {"generationtime_ms": 0.69} — the results key is absent entirely. It is not an empty array and not null. Same for queries shorter than 2 characters. Type it as optional: results?: GeocodingResult[].

Fields worth knowing: admin1 is the state or region and admin2 the county — both are optional, absent for many places. You need admin1 + country to tell Boulder, Colorado from Boulder, Montana.

Forecast — coordinates to weather

https://api.open-meteo.com/v1/forecast
ParamNotes
latitude, longitudeRequired. WGS84.
dailyComma-separated variable list (below).
timezoneUse auto to resolve from coordinates.
forecast_daysDefault 7.

Useful daily variables: temperature_2m_max, temperature_2m_min, apparent_temperature_max, precipitation_sum, precipitation_probability_max, wind_speed_10m_max, wind_gusts_10m_max, uv_index_max, sunrise, sunset, weather_code.

GET /v1/forecast?latitude=40.01&longitude=-105.27&daily=temperature_2m_max,precipitation_probability_max,wind_speed_10m_max&timezone=auto&forecast_days=3

{
  "timezone": "America/Denver",
  "elevation": 1635.0,
  "daily_units": {
    "time": "iso8601",
    "temperature_2m_max": "degC",
    "precipitation_probability_max": "%",
    "wind_speed_10m_max": "km/h"
  },
  "daily": {
    "time":                          ["2026-07-21", "2026-07-22", "2026-07-23"],
    "temperature_2m_max":            [35.0,  34.7,  32.8],
    "precipitation_probability_max": [13,    30,    94  ],
    "wind_speed_10m_max":            [21.8,  24.3,  21.4]
  }
}
The columnar problem

daily is columnar — parallel arrays, one per variable, aligned by index. Day 0 is time[0] + temperature_2m_max[0] and so on. There is no per-day object. Turning this into DailyForecast[] is the job of the transform layer in Lesson 9.

Units are not inside daily — they live in the sibling daily_units object. Don't hardcode the degree symbol: pass temperature_unit=fahrenheit if you want imperial, and read the label from daily_units.

Sanity-check from the terminal

Before writing any code against an endpoint, call it raw. This is the fastest way to learn a new API and it settles arguments about response shape instantly.

curl "https://geocoding-api.open-meteo.com/v1/search?name=Boulder&count=2"
